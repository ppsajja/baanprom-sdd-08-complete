## สภาพแวดล้อม

- เครื่องเดียว CPU 2 ตัว หน่วยความจำ 7 GB PostgreSQL 16 หลังบ้านโหมด production 2 process และผู้ยิงโหลด อยู่เครื่องเดียวกัน แย่ง CPU กัน (เหมือนรอบ R1)
- ไม่ใช่เครื่องขนาดจริงตามคำตอบ Q-68 (4 CPU ฐานข้อมูลแยกเครื่อง ผู้ยิงโหลดคนละเครื่อง) ผลจึงยังไม่ใช่ผลตรวจรับของ AC-07-08
- ข้อมูลจาก uat_seed.py: ลูกค้า 30 ราย ช่าง 10 คน ช่วงเวลา 220 ช่วง บัญชีทดสอบ 40 บัญชี
- ทุกคำขอมี token (CR-11) การตรวจ token อ่านฐานข้อมูล 1 ครั้งต่อคำขอ ซึ่ง R1 ไม่มี

## สิ่งที่แก้ระหว่างรอบ (ประสิทธิภาพที่ทำได้จริง)

1. GAP-42 รอบแรกพบว่าการตรวจ token ใหม่ (CR-11) ถือ connection ของฐานข้อมูลไว้ระหว่างรอเธรดของ endpoint 500 คำขอพร้อมกัน pool 15 connection หมด ทุกคำขอค้าง 30 วินาทีแล้วล้ม แก้ด้วยคืน connection หลังตรวจ token และตั้งขนาด pool เท่าจำนวนเธรด (40) หลังแก้ 500 จาก 500 สำเร็จ
2. GAP-41 การเชื่อมต่อที่ใช้ซ้ำ (keep-alive เบราว์เซอร์ใช้เสมอ) ช้าเพิ่มราว 40 มิลลิวินาทีเมื่อ uvicorn รันหลาย process (วัดด้วย curl GET /health 0.002 เป็น 0.045 วินาที) process เดียวไม่มีอาการ ตั้ง TCP_NODELAY ผ่าน backend/app/ops/serve.py แล้วหาย รอบ B เทียบรอบ A ยืนยันผล
3. คำค้นช่วงเวลาของช่างทุกคนรวมเป็นคำค้นเดียว (เดิม 1 คำค้นต่อช่าง) และ index 8 ตัวใน m004 ผลของข้อนี้ไม่ได้วัดแยก (รอบ R1 ทีมเคยลองรวมคำค้นแล้วดีขึ้นราว 3 ใน 100) จึงไม่อ้างว่าข้อนี้ทำให้ผ่าน
4. ล็อกแถวช่วงเวลา (SELECT FOR UPDATE) ตอนล็อกและจอง กันสอง process ล็อกช่วงเดียวกัน ไม่ได้ทำเพื่อความเร็ว

## วิเคราะห์

- ความหมายใหม่ของ AC-07-08 (Q-68) ทำให้ผลเปลี่ยนจาก "ไม่ผ่าน" เป็น "ผ่าน" บนเครื่องเดิม นี่ไม่ใช่การปรับเกณฑ์ให้ผ่าน เกณฑ์ใหม่มาจากคำตอบของเจ้าของว่า 500 คนหมายถึงอะไร (EV-051) และคำตอบนั้นมาก่อนการวัด
- แบบ 500 คำขอในวินาทีเดียวยังไม่ผ่านเหมือน R1 เพราะงาน 500 คำขอใช้ CPU ราว 5 วินาทีบนเครื่อง 2 CPU ที่แบ่งให้ผู้ยิงโหลด เป็นข้อจำกัดของเครื่อง ไม่ใช่ของโค้ด และไม่ใช่เกณฑ์แล้ว
- AC-09-12 ช้าลงจาก 0.30 เป็น 0.56 วินาที (ยังผ่าน) เพราะการกดออกเดินทางตอนนี้อ่านและเขียนการตอบรับของช่าง (CR-12) และตรวจ token ต้องดูอีกครั้งบนเครื่องจริง
- ช่องว่างที่เหลือบนเครื่องนี้: ที่ 100 ครั้งต่อวินาที p95 ยังต่ำกว่า 0.1 วินาที
